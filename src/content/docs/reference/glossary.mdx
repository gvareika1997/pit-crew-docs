The words you meet in a run: at a gate, in a pull request, in the run report. Each one has one meaning. The definitions come from the plugin's own vocabulary file, `CONTEXT.md`, which defines 103 terms; this page shows the 61 a user sees.

## Planning and gates

### Assumption

A point pit-crew decides without asking and lists in the gate's "Closed without asking" block with its source (`source_kind`: code with `path:line`, data, the person's words in this conversation, or a decision approved earlier in the run). A ticket is never a source. An assumption with no source is a question.

### Real question

A question with at least two reasonable answers that lead to different code or design, which reading the code, the data or the conversation cannot settle. Anything else is an assumption, not a question.

### Closed without asking

The gate block listing the points the interview closed without a question because they do not apply by construction or a cited source already settles them (a `path:line`, DEV or replica data, the person's words, an approved decision of the run; never a ticket), each with that source. Approving the gate confirms them all; naming one in the answer reopens it as a real question.

### Slice

The part of one repo's change that delivers a behavior verifiable on its own (`verifies`) and that one Builder finishes within its turn budget. Slices split by behavior, not by layer; a split by layer survives only inside a staged mass change.

### Mockup option

One clickable visual proposal for one screen, with mock data, representing a distinct layout, flow or interaction approach. It is a reference to implement from, not a pixel-exact specification.

## Testing and evidence

### Test spec

The list of test paths per acceptance criterion, each with its preconditions and expected result, happy and failure paths alike.

### Case

One acceptance criterion with its outcome in DEV: verified, partial or not tested.

### Evidence

What was observed in DEV that backs the status of an acceptance criterion: the response, the record, the log or the screen.

### Carried evidence

Evidence obtained on an earlier commit that still stands for the current head because every file changed since then is documentation, tests or the glossary, came from the base through a clean merge-forward, or nothing changed at all; it carries that diff as proof.

### Case designer

The testing role that writes the test spec from the approved acceptance criteria and later judges the collected evidence against it.

### Configurator

The testing role that prepares the environment and the test data a test spec declares, and removes what it created.

### Tester

The testing role that runs the test spec paths in DEV and returns raw evidence, without grading it.

### Fixture manifest

The record of every piece of data or environment the Configurator created for one run, used to remove it afterwards.

### Orphan fixture

Test data or an environment prepared for a criterion that no longer exists, or for a run that ended before testing. It is removed, never left in DEV.

### Startup gate

The proof, before a run closes, that every backend service the run deployed reaches ready on its latest commit according to its own health checks. A repo may also declare a local startup command that runs before the push.

## Review and pull requests

### First judge review

The single full review of the whole change that `df-judge` does in round 1, before any confirmation round. It is the only judge dispatch that reads the code for new defects across every repo.

### Confirmation review

A `df-judge-recheck` dispatch (rounds 2-3 and the final check) that only verifies the previous findings are fixed and looks for new ones inside the fix diff.

### UI review

The step where `df-ui-reviewer` captures each screen a diff touches (and each mockup and the plan page before they publish) in light, dark and 375px, critiques the images and the diff against the UX checklist, and returns findings ranked Critical, Important or Minor, each grounded in a pattern the repo already has. Critical and Important are applied in one round with one recapture. The captures live in the run folder and on the run's claude.ai page, never in git.

### Universal check

A review check valid on any repo of that stack regardless of team conventions.

### Repo rule

A convention the reviewed repo declares in its own guidance (`CLAUDE.md`, `AGENTS.md`, docs) that the review applies only in that repo.

### Round

One cycle of comments on a PR: wait for every expected automated reviewer (bounded), read what they raised, answer every thread, and push at most one commit with the fixes. Round 1 is the one that runs before the tests; a PR has at most 5.

### Automated reviewer

A tool that reviews PRs with no human in the loop (the `review` role names them). A round waits for the ones the repo declares under `## pit-crew: review bots`, else those seen on its recent merged PRs; identifiers keep the existing `bot` spelling.

### Unanswered bot finding

A root finding from a bot account with Major or Critical severity (or the words the repo declares) that has no non-bot reply classifying it with a reason, nor a reply citing the commit that fixes it, on the current head.

### Minor finding

A bot comment labelled Minor or NIT. The label is the bot's; the round class `minor` (`pit-crew:pr-comment-resolution` §7) is a fix in executable code that the run judged small, and a "Minor" that is really a behaviour defect is a `grave` round.

### Merge-forward

A merge of the base branch into the PR branch to bring it up to date, without changing what the PR proposes.

### PR own files

The files the PR changes against its base branch; what arrives from the base through a merge-forward is not one of them.

### High-risk change

A change the PR declares a one-way door in its `**Door:**` line: what stays behind after a revert. Only a high-risk change must carry a success signal.

### Success signal

What is counted in production, as a log line or a metric the service itself emits on the change's normal path, to confirm a high-risk change worked. It lives in a PR-body section whose heading holds «éxito», «success» or «verif», with fenced `logql` or `promql` blocks, the format a deploy monitor reads. No threshold or window: the monitor compares the same span before and after the deploy. A line logged only at error or warn level is a guard: zero is the good result and the section says so.

## Deploy

### Deploy driver

Who decides when each canary step of `/pit-crew:deploy` advances: the person or the agent. Chosen once per run (by flag or one question) and recorded in the run's state. With the person driving, the agent only reads, reports and recommends.

### Safety stop

A point where `/pit-crew:deploy` stops and asks instead of advancing: a merge the session denies, an active freeze, a busy environment, a timeout, a rollback or `Degraded`/`Aborted` rollout, an owner-lock `403`, errors climbing, or an observation window with nothing observed. Anything else runs without a question once the deploy is invoked.

## How a run ends

### Fix round

A new implementation or test pass after a red build, a red test or a judge finding, counted in `fix_rounds`. A normal fix round does not make a run retried.

### Clean run

A run that finished with no block, no Builder escalation, no turn-budget continuation and no fix rounds at the cap. It writes its local report and publishes no retro.

### Retried run

A run with a lite-to-full Builder escalation, a turn-budget continuation or `fix_rounds` at the cap. Together with a blocked or needs-input run, the only runs that publish a retro.

### Retro

The review of what a run learned. It runs right after the PRs open and again at the end of phase 3 only when something new happened since; tool lessons go to the tracker's retro project, and a knowledge-base page the run proved wrong against `origin/<base>` is corrected through the drift fix.

### Away

A human wait recorded when a run shows no activity for more than 30 minutes: neither work nor a wait on a specific person or machine. A gate or question wait keeps its first 30 minutes and the rest becomes away.

### Abandoned

The outcome of a run that never closed and showed no activity for more than 24 hours, declared afterwards, on the next session start (telemetry hook), once per run.

## Bug triage

### Triage

A read-only investigation that establishes the expected behavior, the observed behavior and the root cause of a problem, and ends in a report without fixing it. Its only write is correcting knowledge-base drift (a block of a page that differs from the base branch and is not the symptom). Runs alone (`pit-crew:triage`) or before planning a bug fix.

### Triage mode

The depth of a triage, full or quick, which decides what it delivers. Inside a run it follows the task type.

### Root cause

Why the observed behavior happens, stated with a certainty: confirmed, probable or undetermined.

### Raw report

A message pasted as it is from a chat, written by someone else, with no ticket. Triage investigates it first, whatever its wording.

### Not a bug

A triage verdict: the behavior is by design, a misunderstanding, a data or configuration problem, or a feature request. The run stops before planning a fix and asks what to do.

### Business contract

The behavior the business expects (rules, owners, onboarding requirements) as the company knowledge base (the `docs` role) describes it. It states the intended rule; the code on the base branch states the current behavior.

### Drift finding

A difference between what a knowledge-base page says and what the base branch does. Pre-existing and not the reported symptom: pit-crew fixes the block of the page. Matching the symptom of a triage: a candidate cause, and the page is not edited.

## Product mode

### Product mode

The way to use Pit Crew for people without a technical profile: only business questions and plain summaries; Pit Crew settles the technical part and takes the request to a change proposal ready for approval.

### Big decision

A technical choice of weight (how users are identified, where secrets are kept, a new database, the technology of a new service, new infrastructure, background communication between services). Pit Crew posts a summary to the support channel for IT to validate, and the person chooses to wait or to continue. A new table or endpoint is not one.

### Technical guide

The technical input a product person offers on their own. It orients but does not bind: the design may depart from it, with the reason written down.

### Delivery to a technical person

The moment the change proposal is ready and the product person chooses who approves it; once approved, they publish it themselves.

## Brainstorm

### Initiative

Work too big for one ticket, split into deliverables and decided in a brainstorm before any ticket exists. In a tracker that has projects it is one project.

### Deliverable

A part of an initiative that can ship and be verified on its own. In a tracker that has milestones it is one milestone of the initiative's project; `/pit-crew:plan` creates its ticket when it starts.

### Focus statement

Four parts the person confirms before a brainstorm researches anything: the problem, who it hurts, what success looks like and what is out of scope.

### Wild idea

A deliberately far-fetched idea a brainstorm shows to provoke the person's own thinking. It is marked as such, never counted as an alternative and never recommended.

## Roles and packs

### Role

A job an external tool does for the pipeline. There are nine: `tracker`, `docs`, `env`, `logs`, `data`, `review`, `deploy`, `events`, `stack`. Pipeline text names a role and a verb (`env.up`), never the tool; a role that is off skips its step and is recorded (`skills/pipeline/resources/roles.md`).

### Adapter

The guide that says how one tool fills a role: each verb with its call, the settings it reads and its limits. It names no value of one company.

### Binding

What an installation supplies for a role: the adapter, the MCP tool id that fills each verb with its access, and the settings (values). `scripts/roles.cjs` resolves it from the packs, the user config and the repo config.

### Pack

A plugin that carries the bindings, adapters and MCP servers of one organisation (`pack.json` at its root), installed beside the core.

## Setup and access

### First-time setup

The guided conversation, started by hand with `/pit-crew:setup`, that leaves a person's local Claude Code config ready for pit-crew and can be repeated later as a health check.

### Cleanup

Removing from a person's config the MCP servers and plugins that pit-crew does not need, always after a backup and an explicit confirmation, and never touching their `CLAUDE.md`, permissions or hooks.

### Indispensable, recommended and optional tool tiers

Three levels of tool: pit-crew does not work without the indispensable one; the recommended one improves use a lot and is suggested strongly; the optional one is offered only to whoever wants it, one at a time.

### Never configured

No credential is set on the machine for that access (row `cause: not_configured`). The preflight says so without calling the network, and names the variable to set.

### Rejected access

A credential that is set on the machine but that the service refuses when the preflight tries it (row `cause: rejected`). The fix is to renew it, then `/mcp` reconnect so the session drops the old one.

### No response

The service does not answer within the preflight's time limit, or answers with a server or network error (row `cause: no_response`). Usually the network or the service itself, never the credential.
