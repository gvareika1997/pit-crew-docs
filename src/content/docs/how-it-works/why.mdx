Systems engineering can now look like production engineering.

Until now, a systems engineer was closer to a craftsman who designs the building and also lays every brick by hand. You wrote the code line by line. The bottleneck was typing.

A production engineer does not stand at the press and stamp each part. They design the product, the process and the quality controls, and they answer for what leaves the plant. The machines make the parts to the tolerances the engineer set. When a part comes out wrong, the engineer does not stamp faster. They fix the process.

With agents, you can work that way. The agents write the code. Your job is to think the whole problem through, decide how it is built, make sure it is built well and take it to production.

| Production engineer | Systems engineer with Pit Crew |
|---|---|
| Designs the product, the process and the tolerances | Designs the solution, the architecture, the contracts and the path to production |
| The machines make the parts | The agents write the code |
| Quality control on the line, not only inspection at the end | Tests, review and evidence while the change is built |
| Answers for what leaves the plant | Answers for what reaches production and works |
| When it goes wrong, improves the process | When it goes wrong, improves the design, the tests and the tools |

Pit Crew is the line. It gives each of those rows a place to happen.

## What changes in your day

### Your work moves to the start

You spend your time on two decisions, and both come before any code exists:

- **Gate 1a · business.** What the change does, for whom, and how you will know it works. Plain words, no technical vocabulary.
- **Gate 1c · architecture.** Which services change, which data changes, the contracts between them, and the risks.

This is where you design. Each gate closes with a two-line recap, one business line and one architecture line. That recap is what you approve. The final report repeats it word for word, so you can compare what shipped with what you agreed to.

The `quick` and `hotfix` lanes ask once. See [Where you work: the two gates](../your-two-gates/) and [Lanes](../lanes/).

### You set the tolerances

A production engineer writes down the tolerance before the machine runs. Here the tolerances are the acceptance criteria you approve at Gate 1a and the design you approve at Gate 1c. Everything after is measured against them: the judge reads the diff against them, and the PR reports each criterion as proved or not tested.

The repo's own rules are tolerances too. Pit Crew follows the `CLAUDE.md` of each repo. A repo without one gets generic code.

### The agents build

After you approve the architecture, the run checks whether the session can write files. If it can, it continues on its own to green pull requests and returns the links. It does not stop to ask between phases. It stops only for an action on production or a secret already committed.

It implements in a git worktree, never in your clone. See [What the agents do](../what-the-agents-do/).

### Quality control is on the line

Inspection does not wait for the end. The run tests while it builds, an adversarial judge attacks the diff before the push, a pre-push gate scans for secrets, and the PR carries the evidence for each criterion. A criterion the run could not prove is reported as not tested. It never closes green on a guess. See [Guarantees](../guarantees/).

### You answer for production

The run leaves the PRs green with their evidence. A person still reviews and approves them. Then you start the merge and the rollout with `/pit-crew:deploy`, and you decide at each safety stop: a freeze, a busy environment, a canary window with nothing observed, a rollback.

:::note[Roadmap: the path to production is not unattended]
Today the unattended part of a run ends at green pull requests. Merging and rolling out happen only when you type `/pit-crew:deploy`. A run that carries an approved change to production on its own does not exist. Read every "the agents do the rest" on this site as "up to the PR".
:::

### When it goes wrong, you fix the process

A run that was blocked or retried earns a retro, and with a `tracker` role connected its improvements become issues. The lesson belongs in the process, not in typing faster: a sharper acceptance criterion, a clearer `CLAUDE.md`, a test that would have caught it. See [State and reports](../state-and-reports/).

## What stays yours

| Yours | The agents' |
|---|---|
| The business spec and its acceptance criteria | The business draft you correct and approve |
| The design: services, data, contracts, risks | The decision table and the plan page you read |
| The PR approval | The diff, the tests and the evidence in the PR body |
| Starting the deploy and deciding at each safety stop | Merging the approved PRs and watching the rollout, once you start it |
| Fixing the process when a run goes wrong | The retro that says what blocked or surprised it |

## What this is not

| It is not | What it does instead |
|---|---|
| An auto-merger | Phases 1 to 3 end at PR links. Only `/pit-crew:deploy`, run by you, merges. |
| An unattended path to production | You start the deploy and decide at its safety stops. See the roadmap note above. |
| A replacement for CI | Phase 3 runs the test scope sized for each repo, never the whole suite. CI owns broad validation. |
| A source of conventions | It follows the `CLAUDE.md` of each repo. |
| A guarantee of full coverage | A criterion it cannot prove, for example with no `env` role connected, is reported as not tested. |
| A permission bypass | It probes whether the session can write. It cannot change the permission mode. |
| A tool that sends your data by default | Telemetry is off until you or a pack turn it on. See [Telemetry](../../roles/telemetry/). |

## What it asks of you

### A precise prompt or a ticket

Start from a ticket, or from a prompt that says what, where and for whom. "Integrate provider X in service Y to process payins in countries Z" works. "Integrate X" does not. A raw report from someone else, such as a chat thread, can go in as it is. Pit Crew triages it first and may conclude it is not a bug. In that case it stops and asks what to do.

### A `CLAUDE.md` in the repo

Write down the repo's conventions, build and test commands, and anything an agent would get wrong. Pit Crew reads repo content as data. It never takes it as an instruction to run a command or widen scope.

### Real attention at the two gates

Read the recap and the plan page before you approve Gate 1c. Points the run settled without asking appear in a "Closed without asking" block, each with its source. Approving the gate confirms them all. After Gate 1c there is no human step until the PR links, so approve only what you would ship.

### A PR review

A person reviews and approves the PRs. After that, you decide when to run `/pit-crew:deploy`.
