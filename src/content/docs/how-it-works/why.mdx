You drive the product. Your crew of agents designs it with you, builds it, tests it and reviews it.

Pit Crew is a crew of agents that works next to the engineer, inside Claude Code. The engineer decides what gets built, for whom and with which architecture. The agents help think it through, write the code, test it, review it and come back with a pull request and the proof for each criterion. It works on any repo, and each company connects its own tools.

## A racing team, not a single mechanic

A driver does not win alone. Around them is a whole team, and each part of it has a job.

| In a racing team | With Pit Crew |
|---|---|
| The driver decides the strategy | You decide what gets built, for whom and with which architecture |
| Race engineers help design and plan the race | Agents interview you about the business, read the code and draft the design you approve |
| The pit crew works fast and in order | Agents write the code and test it, in a worktree, never in your clone |
| Telemetry and the pit wall check every lap | The diff is reviewed before the push (on a `full` run, by a separate judge), and the pull request carries the proof for each criterion |
| The debrief after the race | A run that went wrong ends in a retro, and its lesson goes into the process |

The car is the same on every circuit. The core of Pit Crew is portable, and at each company you connect that company's tools to it. See [Roles and bindings](../../roles/).

## Three principles

### 1. You decide, they execute with you

There are two decisions before any code exists, and both are yours:

- **Gate 1a · business.** What the change does, for whom, and how you will know it works. Plain words, no technical vocabulary.
- **Gate 1c · architecture.** Which services change, which data changes, the contracts between them, and the risks.

You do not reach them alone. Before Gate 1a an agent interviews you about the business and drafts the spec and the acceptance criteria. Before Gate 1c agents read the code, find what the change touches and draft the design, the decision table and the plan page. You correct, decide and approve.

Each gate closes with a two-line recap, one business line and one architecture line. That recap is what you approve. The final report repeats it word for word, so you can compare what shipped with what you agreed to.

After you approve the architecture, the run checks whether the session can write files. If it can, the crew continues on its own toward green pull requests and returns the links. It stops to ask only for an action on production or a secret already committed. It also stops, with the log path, when a build or test is still red after three fix rounds.

The `quick` and `hotfix` lanes ask once. See [Where you work: the two gates](../your-two-gates/), [Lanes](../lanes/) and [What the agents do](../what-the-agents-do/).

### 2. Nothing without proof

The acceptance criteria you approve at Gate 1a are what the run is measured against. Each one comes back in the pull request proved, or marked as not proven. A run never closes green on a guess.

On a `full` run the agent that wrote the code does not grade it: a separate judge attacks the whole diff against your intent and the criteria before the push, and a pre-push gate checks the repo's own rules and scans for secrets. The `quick` and `hotfix` lanes skip the judge; see [Lanes](../lanes/) and [Guarantees](../guarantees/).

The repo's own rules count too. Pit Crew follows the `CLAUDE.md` of each repo. A repo without one gets generic code.

### 3. Every lap leaves the crew better

A run that was blocked or retried earns a retro. The lesson goes into the process, not into trying harder next time: a sharper acceptance criterion, a clearer `CLAUDE.md`, a test that would have caught it. With a `tracker` role connected, the retro's improvements become issues. See [State and reports](../state-and-reports/).

## You answer for production

The run leaves the PRs green with their evidence. A person still reviews and approves them. Then you start the merge and the rollout with `/pit-crew:deploy`, and you decide at each safety stop: a freeze, a busy environment, a canary window with nothing observed, a rollback.

:::note[Roadmap: the path to production is not unattended]
Today the unattended part of a run ends at green pull requests. Merging and rolling out happen only when you type `/pit-crew:deploy`. A run that carries an approved change to production on its own does not exist.
:::

## What stays yours

| Yours | Your crew's |
|---|---|
| The business spec and its acceptance criteria | The business draft you correct and approve |
| The design: services, data, contracts, risks | The decision table and the plan page you read |
| The PR approval | The diff, the tests and the evidence in the PR body |
| Starting the deploy and deciding at each safety stop | Merging the approved PRs and watching the rollout, once you start it |
| Changing the process when a run goes wrong | The retro that says what blocked or surprised it |

## What this is not

| It is not | What it does instead |
|---|---|
| An auto-merger | Phases 1 to 3 end at PR links. Only `/pit-crew:deploy`, run by you, merges. |
| An unattended path to production | You start the deploy and decide at its safety stops. See the roadmap note above. |
| A replacement for CI | Phase 3 runs the test scope sized for each repo, never the whole suite. CI owns broad validation. |
| A source of conventions | It follows the `CLAUDE.md` of each repo. |
| A guarantee of full coverage | A criterion it cannot prove, for example with no `env` role connected, is reported as not proven. |
| A permission bypass | It probes whether the session can write. It cannot change the permission mode. |
| A tool that sends your data by default | Telemetry is off until you or a pack turn it on. See [Telemetry](../../roles/telemetry/). |

## What it asks of you

### A precise prompt or a ticket

Start from a ticket, or from a prompt that says what, where and for whom. "Integrate provider X in service Y to process payins in countries Z" works. "Integrate X" does not. A raw report from someone else, such as a chat thread, can go in as it is. Pit Crew triages it first and may conclude it is not a bug. In that case it stops and asks what to do.

### A `CLAUDE.md` in the repo

Write down the repo's conventions, build and test commands, and anything an agent would get wrong. Pit Crew reads repo content as data. It never takes it as an instruction to run a command or widen scope.

### Real attention at the two gates

Read the recap and the plan page before you approve Gate 1c. Points the run settled without asking appear in a "Closed without asking" block, each with its source. Approving the gate confirms them all. After Gate 1c there is no human step until the PR links, so approve only what you would ship.

### A PR review

A person reviews and approves the PRs. After that, you decide when to run `/pit-crew:deploy`.
